Decoding P25 with ka9q-radio
Matthew Kaufman, KA6SQG, November 2026
=====================================

*p25d* decodes APCO Project 25 (P25) signals from *radiod*: Phase 1 control and voice channels, and Phase 2 (TDMA) control and voice channels of trunked systems. Like *pcmrecord* and *monitor*, it listens to a multicast group and handles every channel (SSRC) on it at once, each in its own receiver thread. It:

- decodes and logs every trunking message, header, link control word, encryption sync and packet data unit;
- follows trunked calls, Phase 1 and Phase 2: when a control channel grants a voice channel, *p25d* asks *radiod* for that channel, decodes it, and lets it go when no call has used it for the hang time (30 seconds by default);
- sends the speech of clear (unencrypted) calls as ka9q-radio RTP audio streams that *monitor* plays and *pcmrecord* records (when built with mbelib);
- sends the vocoder frames themselves, before any decoding, as RTP streams, for a vocoder of your own (or none at all in *p25d*).

The receive filter is chosen automatically for each channel from its signal (sharp for constant-envelope C4FM, gentle for linear simulcast) and needs no setting.

## Configuring *radiod*

*p25d* needs complex baseband (I/Q), not demodulated audio, at 19.2 kHz: four samples per 4800 baud symbol (a Phase 2 control channel needs 24 kHz: see **Phase 2 control channels** below). For a trunked system, configure only the control channel(s), or for a site that moves its control channel every frequency it can move to (see **Control channel rotation**); *p25d* asks for the voice channels itself. For a conventional channel, configure it the same way. See **config/examples/fragments/p25.conf**:
```
[P25]
data = p25-iq.local
mode = iq
samprate = 19200
low = -5k
high = +5k
encoding = f32le
agc = no
gain = 60
freq = "857m98125"
```
Each frequency becomes a separate channel with its own SSRC, all sent to **p25-iq.local**. With the default 20 ms block time, 19.2 kHz is 384 samples per block.

The *iq* preset turns on the linear demodulator's AGC, which scales I and Q together. *p25d* sets its own level, so turn the AGC off and use a fixed gain. With 32-bit floats (**f32le**) there's no clipping, so the gain only has to be roughly right. 16-bit integers (**s16be**, half the network traffic) also work: either keep 30 dB or more of margin with a fixed gain, as the WSPR example does, or leave the AGC on with **hang-time = 0** as the HFDL example does. *p25d* accepts **s16be**, **s16le**, **f32le** and **f32be**; it ignores mono and Opus streams.

### Voice channels created on demand

A voice channel *p25d* asks for is made in the control channel's form: the same sample rate, encoding, filter, gain and AGC setting, and the same data group. Set these on the control channel as above. (On a Phase 2 control channel, whose rate is 24 kHz, a Phase 1 voice channel is asked for at 19.2 kHz with a -5 to +5 kHz filter instead, the form above.) Three things come from elsewhere:

- *radiod* builds a new channel from its **[global]** section, and two of its settings can't be changed by a request. **data =** must be set in [global] (without it *radiod* can't create channels at all); using the control channel's group there is simplest. **ttl =** in [global] is the new channels' multicast TTL: **ttl = 0** keeps them on the *radiod* host, so a *p25d* on another machine would see the control channel (if its own section says **ttl = 1**) but none of the voice channels.
- The front end must cover the control channel and the system's voice frequencies at the same time. Set the front end's frequency in *radiod*'s hardware section (**frequency =**), which also locks it, and choose it so that the whole system is inside what the front end delivers. Where that band lies depends on the hardware: an Airspy R2 at 20 MHz sampling, for one, delivers roughly 0.6 to 9.4 MHz *below* the frequency it is given, so it is set above the system's highest channel. *p25d* never asks for a channel outside the coverage *radiod* reports: a *radiod* whose front end is not locked would retune it to reach the new channel, and every channel left outside the new coverage, the control channel perhaps among them, would go quiet. It logs such a frequency once and doesn't ask again.
- *p25d* sends its requests to the *radiod* that sent the control channel; it learns the command address from the channel's status, so there is nothing to configure. Commands go out with TTL 1, as *tune* and *control* send them. A channel is known by its SSRC together with the address and port it comes from, so two *radiod*s on one host are kept apart. A voice channel is matched to its control channel by the *radiod* command address both name in their status, not by where they come from: *radiod* sends channels with a TTL of 0 from one socket and the rest from another, so a voice channel made from [global] can arrive from another port than its control channel.

A channel is asked for with a lifetime of 10 seconds, so one left behind by a crash goes away by itself, and a host too busy to send a refresh for several seconds does not lose a channel in use. While a call uses a channel, and while it is kept after one, *p25d* refreshes it every half second; a command goes to *radiod* only when a third of the lifetime has passed since the last, so this costs little. When the last call on a channel ends, *p25d* keeps the channel for the hang time (**-H**, 30 seconds by default) and then releases it; when *p25d* exits, or the control channel's stream goes away, its channels are released at once. No release is sent for a channel whose lifetime has already run out: *radiod* has let it go, and a command naming it would only make *radiod* build a new channel from its template. A granted frequency that *radiod* already carries in the same form, to the same data group and port, is used as it is: a channel configured in *radiod* is never sent anything, and one another program asked for is polled to keep it, at the pace of the lifetime its own status shows, and never released. See **Hang time** below.

### Phase 2 voice channels

A Phase 2 (TDMA) voice channel is asked for in the control channel's form too, but with two things changed: a sample rate of **24 kHz** (four samples per 6000 baud symbol; 19.2 kHz is too few for the Phase 2 receiver) and a filter of **-5 to +5 kHz**. The H-DQPSK signal occupies +/-3.6 kHz, so that leaves room for the carrier's offset, keeps the next 12.5 kHz channel out and stays well inside the 12 kHz Nyquist limit. *radiod* needs nothing more for it: with its default 20 ms blocks a 24 kHz channel is 480 samples per block, and the request carries the rate and the filter. (With another **blocktime** the rate must still give a whole number of samples per block, as for any channel.) A Phase 1 control channel itself stays at 19.2 kHz (a Phase 2 one is at 24 kHz: see below). Both timeslots of a TDMA carrier are one *radiod* channel: *p25d* asks for it once, whichever slot's call comes first, and lets it go only when neither slot's call needs it (and the hang time has passed).

## Running *p25d*

```
p25d [options] p25-iq.local [more groups ...]
```
- **-I**, **--input** *group*: add an input group (groups may also be given without -I)
- **-R**, **--pcm-out** *group*: send voice to this multicast group (e.g. **p25-pcm.local**); without it, no audio
- **-F**, **--frames-out** *group*: send the vocoder frames to this multicast group (e.g. **p25-frames.local**); works without mbelib
- **-E**, **--frames-encrypted**: with **-F**, also send the frames of encrypted voice, flagged so
- **-N**, **--name** *name*: name the voice output is advertised under (default p25d; the frames as "p25d frames")
- **-T**, **--ttl** *ttl*: multicast TTL of the voice and frame output (default 0: this host only)
- **-p**, **--tos** *tos*: IP type of service of the voice and frame output (default 184, expedited forwarding)
- **-n**, **--no-follow**: don't follow calls; only decode the channels already there
- **-g**, **--talkgroups** *list*: follow group calls on only these talkgroups, e.g. **2501,2600-2699** (repeatable). This and **-x** choose trunked calls to follow; they don't filter conventional channels
- **-x**, **--exclude** *list*: never follow these talkgroups (repeatable)
- **-a**, **--nac** *list*: decode only these NACs, hex and comma separated, e.g. **443** or **443,2c1** (repeatable). As a P25 radio's NAC squelch: on every channel, conventional, control and voice, data units and Phase 2 LCCH PDUs with another NAC are dropped before anything is done with them (with **-v**, a line says so once). **F7E** or **F7F** in the list let any through. With exactly one NAC given, every receiver starts with it known, so weak frame syncs are taken from the first frame. Default: any NAC
- **-m**, **--max-calls** *n*: follow at most *n* calls at once (default: no limit)
- **-e**, **--encrypted**: follow encrypted calls too (a call is encrypted, for following, when its grant says so). They are logged; their voice is never decoded
- **-H**, **--hangtime** *seconds*: keep a voice channel this long after the last call on it ends, so that the next call there finds it running (default 30; fractions allowed; 0 releases it at once; at most 86400; 3 for the least load)
- **-v**, **--verbose**: more messages; repeat for more detail. At -v each channel also logs a status line
- **-u**, **--update** *seconds*: interval between the -v status lines (default 10)
- **-t**, **--timeout** *seconds*: close a channel after this long without data (default 20)
- **-S**, **--ssrc** *ssrc*: decode only this channel (turns call following off)
- **-o**, **--source** *name-or-address*: accept only this sender (source-specific multicast)
- **-A**, **--iface** *interface*: default multicast interface
- **-l**, **--locale** *locale*: locale for number formatting (default $LANG)
- **-V**, **--version**: show version and exit

SIGUSR1 and SIGUSR2 raise and lower the verbosity while *p25d* runs, as in *radiod*. SIGINT, SIGTERM and SIGQUIT stop it, and its voice channels are released.

*p25d* learns each channel's sample rate, encoding and frequency from the status *radiod* sends alongside the data, so a channel starts a second or so after *p25d* (or *radiod*) does. Lost packets are replaced with zeroes so the symbol timing holds; late and reordered packets are put back in order; gaps longer than a second are skipped.

## Following calls

Any channel on which trunking messages decode (trunking blocks, multi-block trunking packets, or a Phase 2 LCCH), other than a voice channel *p25d* asked for, is a control channel. *p25d* keeps track of its calls: grants and grant updates, the voice channels' link control, headers and terminators, and the site's patches. For each call it decides whether to follow it, and logs it either way.

A trunking block heard on a voice channel is acted on (a grant is a grant), but is not taken as a sign that the control channel is being received. A protected trunking block (encrypted past its opcode and manufacturer) shows only that the control channel is there: it is logged, marked **protected=1**, but its fields are not used. A multi-block trunking packet is used only if the CRC over its data blocks passes as well as its header's; one that fails is ignored.

A followed call's channel is requested from *radiod* when the grant comes, asked for again as grant updates come, and kept alive every half second while the call lasts (see **Voice channels created on demand**). The call ends when a terminator ends it, when the channel is granted to another call, or 3 seconds after the last voice and the last grant; its channel is then kept for the hang time (below) and released if no call comes. The voice channel's receiver starts with the control channel's carrier offset, since both come from the same site.

### Control channel rotation

Some sites move their control channel from time to time among a set of frequencies, which they announce as secondary control channels (*p25d* logs them as **trunk control secondary freq=...** with **-v**). To follow such a site, configure every one of those frequencies in *radiod* as a channel in the control channel's form, as well as the control channel itself; *p25d* decodes them all, and the site follows its control channel from one to the next:

- A channel takes over the site's control role when an RFSS status broadcast decoded there names the same system, RFSS and site, with that channel's frequency as the control channel, and the site's present control channel has been silent for 2 seconds. The site keeps its calls, its voice channels and what it knows; only its channel changes, and a line says so:

```
Sun 22 Nov 2026 10:02:11.400 UTC ssrc 851012 851.012500 MHz NAC 443 control channel moved to 851.012500 MHz ssrc 851012 (was 857.981250 MHz ssrc 857981)
```

- The old control channel becomes an ordinary channel, which the site can then grant as a voice channel like any other configured frequency.
- Until the new channel's RFSS status comes round (every few seconds on most systems), its trunking goes to the site as trunking heard on a voice channel does, so calls granted in that time are followed.
- The silence keeps a site with two control channels on the air at once from passing the role back and forth. A channel whose RFSS status names another site is a site of its own.
- If the new control channel is one *p25d* asked *radiod* for as a voice channel (not configured), *p25d* does not move there, since it would release the channel at the end of its hang time, and logs that it should be configured.
- A call granted, in the moments between the old control channel stopping and the move, on the old control channel's own frequency loses its first voice units until the move (in a generated test, 2 of 16): until then that channel is still the site's control channel and its voice is not decoded as a call's.

Each configured channel runs a receiver all the time, which costs little: in the test on the air *p25d* took under 3% of a core for seven channels. A later version is to use the announced secondary control channels itself: when the control channel goes silent, ask *radiod* for them and look for the control channel there, so that only one control channel need be configured.

### Hang time

Many systems keep a conversation on one frequency: the reply a second or two later is granted the same voice channel, and later calls come back to frequencies used a little earlier. Asking *radiod* for a new channel each time costs a new channel in *radiod*, and the new channel's receiver has to find the carrier, the symbol timing and frame sync again before the first voice (which comes about 0.4 s after the grant on Phase 1). So when the last call on a voice channel ends (by a terminator, a timeout, the channel being granted to another call, or the call no longer being followed), *p25d* keeps the channel in *radiod*, alive and with its receiver running, for the hang time (**-H**, 30 seconds by default). A call there in that time uses it as it is. With none, the channel is released. **-H 0** releases it as soon as its last call ends.

**When the clock starts.** The hang time counts from the end of the last call on the channel. Systems go on naming the frequency in grant updates for a second or two after a call's last voice (up to 1.9 seconds in the survey below, 99th percentile 2.8 s), whether or not anyone replies, and send terminators on the voice channel meanwhile. An update carries no talker, so it can't tell a reply from that hang. Taken as calls, these updates would show as a call after every call (started, then ended with no voice), hold a place under **-m**, and restart the hang clock. So for 3 seconds after a call *p25d* followed (or the hang time, if shorter), a grant update naming the same call on the same channel starts no new call. An explicit grant does, and so does an update naming another talkgroup, and so does voice on the channel: a reply announced only by grant updates is followed from its own voice on the kept channel, from its header or first voice unit, a few tenths of a second later than the update would have announced it. A recorder working per call sees such a reply as a new call, with its talker, starting when its voice does. After a call *p25d* did not follow (not allowed, excluded, encrypted without **-e**, beyond **-m**, or refused by *radiod*), and with **-H 0**, nothing is listening on the channel, so updates start calls and ask for the channel as before; otherwise that reply would be missed.

**The default.** It comes from a survey of 96 hours in November 2026 of four trunked sites in the San Francisco Bay Area: San Mateo (Phase 1, 5 voice carriers), SVRCS West and SVRCS Central (Phase 2, 6 each) and EBRCS Southwest (Phase 2 with some Phase 1, 6). Those systems keep a channel assigned for 0.85 s (Phase 2) to 1.9 s (Phase 1; 99th percentile 2.8 s) after the last voice, and a reply by the same talkgroup on the same frequency always came within 2.75 s. So 3 seconds catches every deliberate reuse and saves about half of all channel requests (49 to 56%) for a quarter to half an idle receiver per site on average. Beyond that a frequency is reused only as the system rotates through its carriers, and on busy systems the saving keeps growing: 10 seconds saves 51 to 60% for about one idle receiver per site (0.6 to 1.3), and the default, 30 seconds, 64 to 84% (95% in the busiest hours of the busiest site) for two to three idle receivers per site on average (1.6 to 2.8). The peak is bounded by the number of voice carriers the site uses whatever the hang time (at 2 seconds or more the peak already reaches all of them), so the longer default costs average load, not peak. **-H 3** is the choice for the least load; quiet systems gain nothing past it.

- A Phase 2 channel serves both timeslots, so it is kept only when neither has a call, and a call on either slot uses it. A channel kept after a Phase 1 call and granted as Phase 2 (or the reverse, which is rare) is simply asked for in its new form and its receiver started afresh, as for a new channel: the first transmission starts as on a fresh channel.
- Nothing of the call that ended carries into the next one on the channel: each call starts clear under the encryption rule (below), and its own words decide. Voice heard on a kept channel with no grant seen (a grant missed) starts a call as on any channel *p25d* asked for, and that call is followed, and heard, only under the same rules (**-g**, **-x**, **-e**, **-m**) as one that was granted.
- **-m** counts calls, not kept channels. Kept channels are bounded another way: at most one per voice frequency the site has granted in the last hang time (a call on a kept frequency uses that channel), and never more than 64 voice channels per control channel, in use and kept together (when that many are there, the one kept longest is released for a new one). Each costs a *radiod* channel and a receiver thread for at most the hang time after its last call.
- When *p25d* exits or the control channel's stream goes away, kept channels are released at once. A call on the other timeslot of a TDMA control channel's own carrier has no channel to keep.
- One *radiod* may serve the control channels of two systems that use the same voice frequency, and *radiod*'s SSRC is per frequency, so both name the same channel. It belongs to the site that asked for it last: when one site asks for a channel the other is only keeping, the other forgets it without releasing it, and the channel's receiver is started again for the asking site. If the other site has a call on it at that moment (both systems heard at once on one frequency), nothing changes, and the second call gets no voice and ends by timeout.
- With **-v**, a line says when a channel is kept, and another when it is reused or released, or let go to another site as above.

Calls not followed: encrypted calls (unless **-e**); talkgroups outside **-g** or inside **-x**; calls beyond **-m**; and calls on frequencies outside the front end.

## Phase 2

A grant of a TDMA channel (a channel identifier the site's IDEN_UP_TDMA says has two slots) names a carrier and a timeslot. *p25d* runs one Phase 2 receiver on the carrier and keeps the two timeslots apart: each has its own call, its own encryption state and its own voice and frame streams.

**Scrambling.** Phase 2 voice and most signalling are scrambled with a sequence made from the system's WACN, system ID and NAC. *p25d* takes them from the control channel: the WACN and system ID from its network status broadcast (NET_STS_BCST), the NAC from its trunking blocks. A control channel sends its network status every few seconds, so it is normally known long before the first grant. If a grant comes first, the channel is asked for at once but nothing scrambled on it is decoded until the network status has been heard (the receiver gets no parameters, so it decodes no voice from a guess); *p25d* says so once, and logs the parameters when they are set.

**The voice channel's signalling** goes to the call tracking as Phase 1's link control does, per timeslot: a MAC PTT opens a transmission and gives the talkgroup and the encryption (as a Phase 1 header does), a MAC END PTT ends the call (as a terminator does), a group or unit voice channel user structure says who holds the slot (as link control does: another talkgroup there ends the call and starts another, another unit is a new talker), and the encryption sync (ESS) of each 2V burst gives the encryption as an LDU2's does. Grants and grant updates carried in MAC structures are acted on like the control channel's. MAC IDLE and HANGTIME end the transmission for the voice output but not the call: as on Phase 1 the call goes on while grants name it, and ends 3 seconds after the last voice and the last grant.

Phase 2 is a trunked mode only: there are no Phase 2 conventional channels. A TDMA carrier configured in *radiod* that carries no LCCH (a voice carrier watched permanently, say) is decoded as Phase 2 at 24 kHz and its MAC messages are logged, but no voice comes from it except as a voice channel granted on a control channel *p25d* follows.

### Phase 2 control channels

A site whose control channel is itself TDMA sends its trunking on one timeslot of the carrier (or both) as the LCCH: unscrambled MAC_SIGNAL PDUs, each with a CRC-16 and the site's NAC (its color code) and up to three MAC structures, the same messages as Phase 1's trunking blocks in their abbreviated and explicit forms (network, RFSS and adjacent site status, identifier updates, secondary control channels, grants and grant updates, patches and so on). The other timeslot may carry calls.

**Configuring it in *radiod*:** as any control channel, but at **24 kHz** (four samples per 6000 baud symbol) with a **-5 to +5 kHz** filter, the form *p25d* asks for a Phase 2 voice channel in:
```
[P25 TDMA control]
data = p25-iq.local
mode = iq
samprate = 24000
low = -5k
high = +5k
encoding = f32le
agc = no
gain = 60
freq = "770m50625"
```
There is no option to set. On a channel at 24 kHz (or more) that it did not ask for, *p25d* runs the Phase 1 and the Phase 2 receivers side by side on the same samples until one of them decodes something that passes its check (Phase 1: a trunking block, header, link control, encryption sync or packet header; Phase 2: any MAC PDU), normally within a few tenths of a second, and keeps that one; with **-v** it says which and when. A channel's modulation doesn't change, so the choice stands. On noise both keep looking. So a Phase 1 control channel (or conventional channel) can be configured at 24 kHz too; below 24 kHz only the Phase 1 receiver runs, as before.

**What comes from the LCCH:** everything a Phase 1 control channel gives. Each structure is logged as the control channel's message (below), and goes to the call tracking exactly as the trunking block it abbreviates would: the site and its band plan, the network status, grants and updates (a multiple grant update as one update per call), unit-to-unit and telephone grants, patches. The site's NAC is the PDUs' color code, and the WACN and system ID come from its network status, so the scrambling of the site's traffic is known from the LCCH itself.

**Calls on the control channel's own carrier.** A grant may name the other timeslot of the control channel's carrier. *p25d* decodes that call from the samples it already has: it asks *radiod* for nothing, and the control channel is never let go when the call ends. The call goes through exactly the same rules as one on any other Phase 2 channel (the same encryption gates, the same streams: a group call's has the talkgroup as its SSRC, any other the control channel's SSRC plus the timeslot number), and is logged with the control channel's SSRC as its voice channel. Only a call *p25d* follows is heard there (**-g**, **-x**, **-e** and **-m** apply as anywhere: **-m** counts it).

**Voice channels granted on it** are asked for as from any control channel: a Phase 2 one at 24 kHz with a -5 to +5 kHz filter, a Phase 1 one at 19.2 kHz with a -5 to +5 kHz filter; each receiver starts with the control channel's carrier offset.

**Multi-fragment messages.** A message too long for one PDU (the forms that name units by their full WACN, system and unit ID, used for units from other systems) is sent as a first fragment followed by continuations in the next PDUs of the same timeslot. *p25d* puts each together and logs it decoded after its fragments. The extended unit-to-unit grant and grant update (0xCF, 0xC7) start and continue a unit-to-unit call as the ordinary ones do (**-e**, **-m** apply alike); the rest (call alert, message and status updates, status query, radio unit monitor, acknowledgement, authentication demand) are logged. A message one of whose fragments is lost is dropped.

Lines:
```
Sun 22 Nov 2026 19:28:37.203 UTC ssrc 770506 770.506250 MHz receiver Phase 2 (TDMA): the first to decode, after 0.29 s
Sun 22 Nov 2026 19:28:37.203 UTC ssrc 770506 770.506250 MHz Phase 2 control channel: LCCH on timeslot 0
Sun 22 Nov 2026 19:28:37.676 UTC ssrc 770506 770.506250 MHz NAC 443 slot 0 MAC NET_STS_BCST chan=lcch pdu=signal lra=0x00 wacn=0xbee00 sys=0x445 ch=3-1360 freq=770.506250 slot=0 class=0x70 nac=0x443
Sun 22 Nov 2026 19:28:42.111 UTC ssrc 770506 770.506250 MHz NAC 443 slot 0 MAC GRP_V_CH_GRANT chan=lcch pdu=signal tg=3001 src=3001001 svc=0x00 prio=0 ch=3-1361 freq=770.506250 slot=1
Sun 22 Nov 2026 19:28:42.111 UTC ssrc 770506 770.506250 MHz NAC 443 call start group tg 3001 src 3001001 voice 770.506250 MHz slot 1 ssrc 770506
```
(the first two with **-v**). The status line of a Phase 2 control channel says **Phase 2 control, LCCH slot 0**, and while the receiver is not chosen yet, both receivers' lines appear, the Phase 2 one saying **receiver not chosen yet**.


Channels configured in *radiod* that no grant names (a conventional P25 channel, say) are decoded as before, with audio under the same rule as everything else. See **Conventional channels** below.

## Voice output

With **-R**, the speech of clear calls is decoded with the IMBE vocoder and sent as 8 kHz mono 16-bit audio, one RTP packet per 20 ms, with status packets as *radiod* sends them, so *monitor* plays it and *pcmrecord* records it. RTP timestamps are *radiod*'s clock, so a recording lines up with the I/Q it came from.

**Encrypted voice is not decoded.** *p25d* labels voice by one rule: the last word wins. A transmission starts clear. A header or encryption sync (Phase 2: a MAC PTT or an ESS) that passed error correction naming any algorithm but 0x80, or link control (Phase 2: a MAC voice channel user structure) with the encrypted service option, makes it encrypted; only a header or sync saying 0x80 makes it clear again. A clear service option says nothing, since some radios never set it in an encrypted call, and nor does protected link control, whose fields are hidden. On a trunked channel the call tracking applies the same rule to the whole call, from its grant on, and voice is decoded only if neither says encrypted. Each voice unit goes out as it arrives, decoded or not; nothing is held back waiting to be confirmed. At a weak signal a damaged word now and then passes its error correction with wrong contents, and under this rule it misleads only until the next header or sync, at most a superframe (360 ms): that much clear speech muted, or that much of an encrypted transmission decoded as noise. An encrypted transmission entered late, or after a fade of more than half a second, is decoded as noise until its first sync (up to 360 ms), unless link control with the encrypted service option comes first. That is accepted: losing clear speech is worse. A transmission ends at a terminator, a new header, the call ending, or half a second without voice, and the next starts clear. Link control naming another talkgroup or talker ends one too, but is seen only after the change, so the encryption stays as the last words left it until the next sync says otherwise.

Any algorithm other than 0x80 counts as encrypted, 0x00 included, with one exception: a Phase 1 encryption sync (LDU2) whose algorithm, key and message indicator are all zero is taken as unencrypted. Some L3Harris console transmissions that are not encrypted send such a sync (sdrtrunk does the same, for that reason); without the exception the rest of the transmission would be silent. It is logged as **algid=0x80 ... (sent as all zeros: taken as unencrypted)**. A header saying 0x00 is not excused, nor is a Phase 2 PTT or ESS: each is a word saying encrypted.

Phase 2 follows the same rule, per timeslot, with a MAC PTT or the ESS of a 2V burst in place of the header and encryption sync. A MAC END PTT, IDLE or HANGTIME ends a transmission, and a voice channel user structure naming another talkgroup or talker starts a new one. As on Phase 1, a fade shorter than half a second does not end a transmission: at most the four voice bursts before the next ESS (16 frames) of an encrypted transmission hidden by it can be decoded.

Streams:

- A trunked group call's stream has the **talkgroup number as its SSRC**, whichever voice frequency carries it, so a listener sees one stream per talkgroup. Talkgroup numbers are unique only within one system: if one *p25d* (or several sharing an output group) follows more than one system, two systems using the same talkgroup number would send on the same SSRC. For now, run one *p25d* with its own output group per system. A way to tell systems apart (an SSRC base per system, a map file, or one output group per system) may be added later.
- A unit-to-unit or telephone call, and any channel without call tracking, uses the voice channel's own SSRC. On a Phase 2 channel, two such calls could be on the channel at once, one per timeslot, so timeslot 0's uses the channel's SSRC and timeslot 1's the channel's SSRC plus one (channel SSRCs are *radiod*'s numbers in kHz, and P25 channels are at least 6.25 kHz apart, so that is no other channel's).
- The status carries the voice frequency and a description such as **P25 TG 2501 src 1118028 "ENGINE 5" NAC 443**: talkgroup (or **P25 unit** and the radio called, or **P25 telephone** and the radio in a telephone interconnect call, which has no source), source, the talker alias when one has been received, and the system's NAC; a Phase 2 call's ends with its timeslot, e.g. **NAC 443 slot 0**. The status also passes on what *radiod* measured on the voice channel the speech came from (signal power in the channel filter, noise density and the filter's edges). That is a measure of the radio signal, not of the decoding: on a simulcast system it can be high while bit errors are many, and those are in the call lines of the log.
- What the tools do with it today: *pcmrecord* puts the description in its messages, in each file's attributes and in the **$d** of an **--exec** command. *monitor* shows the stream's SSRC (for a group call, the talkgroup), the frequency and, from the signal figures, the carrier's SNR, on which it can also vote; it does not show the description, so it shows neither the talker nor the alias.

### The vocoder

IMBE (Phase 1) and AMBE+2 (Phase 2) decoding use mbelib (https://github.com/szechyjs/mbelib), which is optional. If its header **mbelib.h** is found when *p25d* is built, it is used; otherwise *p25d* is built without a vocoder, says so once when it starts, and does everything else. mbelib's own README says it is for educational purposes only and that the algorithms may be covered by patents, so packagers may prefer to build without it. Its speech level is left as mbelib produces it.

## Vocoder frame output

With **-F**, *p25d* sends the vocoder frames themselves, as they came off the air, so you can run your own vocoder (or a hardware one) instead of mbelib. It doesn't need mbelib. Speech (**-R**) and frames can each be on or off. The frame stream follows the same rule as speech: only frames of voice units the rule takes as clear, sent as they arrive. Each channel's frame stream has the same SSRC, description, timestamps and marker bits as its speech stream, so decoding the frames gives exactly the timeline *pcmrecord* records from the speech stream.

With **-E** as well, the frames of voice units the rule takes as encrypted are sent too, flagged encrypted, with the encryption parameters a key holder needs. *p25d* never decodes them; decrypting is the receiver's business. Encrypted and clear frames of a call share one stream, and each packet says which it is. Speech is the same with or without **-E**. On a trunked system encrypted calls are followed only with **-e**, so give both.

### Packets

One RTP packet per 20 ms vocoder frame, to port 5004 of the group. The payload type is **97**. The RTP clock is 8 kHz: the timestamp goes up 160 per frame, and a transmission's first timestamp is *radiod*'s clock at its first frame, as for speech. The marker bit is set on the first packet of each transmission. All numbers are big-endian, and bits are packed most significant bit first:

| Octet | Field |
|---|---|
| 0 | Version, 1 |
| 1 | Codec: 1 IMBE (Phase 1 full rate: 7200 bit/s with error correction, 4400 without), 2 AMBE+2 (Phase 2 half rate: 3600 with, 2450 without) |
| 2 | Flags: 0x01 lost, 0x02 encrypted, 0x04 encryption parameters fresh; other bits 0 (ignore them) |
| 3 | Position of the frame in its superframe, 0-17 (255 in a lost frame) |
| 4 | e0: bits corrected in codeword c0 (IMBE 0-3; AMBE+2 0-4) |
| 5 | IMBE: e4, bits corrected in c4 (0-1). AMBE+2: e1, bits corrected in c1 (0-3) |
| 6 | eT: IMBE, bits corrected in c0 to c6; AMBE+2, e0 + e1 |
| 7 | mbelib's *errs*: IMBE e0; AMBE+2, bits corrected in the information bits of c0 |
| 8 | mbelib's *errs2*: IMBE eT; AMBE+2, bits corrected in the information bits of c0 and c1 |
| 9 | ALGID (0x80 clear; 0 if none received yet in this transmission) |
| 10-11 | Key ID |
| 12-20 | Message indicator (72 bits) |
| 21- | The information bits after error correction: IMBE 88 bits (u0 to u7) in octets 21-31; AMBE+2 49 bits (u0 to u3) in octets 21-27, the last 7 bits zero |
| then | The frame as received, before error correction: IMBE 144 bits (interleaved, c1 to c6 still masked) in octets 32-49; AMBE+2 72 bits (descrambled) in octets 28-36 |

A packet is 50 octets for IMBE, 37 for AMBE+2. A receiver should check the version and the length and ignore packets it doesn't understand; a change to this layout gets a new version.

**Positions.** IMBE: the nine frames of an LDU1 are 0-8, those of an LDU2 9-17. AMBE+2: the four 4V bursts of a superframe carry frames 0-15 and the 2V frames 16 and 17, counting from the first 4V after a 2V (or after the MAC PTT).

**Encryption parameters.** A header (Phase 2: a MAC PTT) carries the parameters for the first superframe, and each LDU2's encryption sync (Phase 2: the ESS completed in a 2V) those for the next superframe. Every frame carries the parameters received last, with their error correction passed, before its own superframe began, in the same transmission, as received: *p25d* doesn't advance the message indicator itself. The fresh flag says they came in the unit just before the superframe (the header, or the previous superframe's LDU2 or 2V); without it the sync that should have been there was lost, and the values are older ones. Clear frames carry the same fields (ALGID 0x80).

**Lost frames.** A voice unit lost on the air (counted from the receiver's symbol clock), up to half a second of them, is sent as lost frames: packets with the lost flag, the codec and nothing else, at the timestamps the frames would have had. They're sent rather than left as a timestamp gap because the vocoder must be told: the speech stream has repeated, then muted, frames there, and a receiver that decodes a lost frame as a repeat gets the same samples. A gap in RTP sequence numbers is loss on the network: treat each missing 160 timestamps as a lost frame. A longer gap on the air ends the transmission, and the next starts with a marker.

**Decoding.** The repeat and mute rules a vocoder needs come from the counts. For IMBE, TIA-102.BABA's: with the error rate eR = 0.95 eR + 0.000365 eT, repeat the last frame's parameters when e0 >= 2 and eT >= 10 + 40 eR (or the parameters are invalid), mute while eR > 0.0875 or after more than three repeats in a row; reset at a marker; a lost frame is a repeat. This is what *p25d*'s speech output does. For AMBE+2, *p25d* passes octets 7 and 8 to mbelib's **mbe_processAmbe2450Dataf()** with its own rule (repeat when *errs2* is over 3, mute after three repeats), and a lost frame as the last frame again with *errs2* 4.

What existing decoders need:

- mbelib: octets 7 and 8 as *errs* and *errs2*, and the information bits unpacked one per byte as **imbe_d[88]** or **ambe_d[49]**.
- JMBE: the raw frame octets as they are (18 for IMBE, 9 for AMBE+2): it does its own error correction.
- DSD's .imb and .amb files: octet 8 then the information octets. DSD puts the 49th AMBE bit in an octet of its own, so repack that one.
- DVSI AMBE-3000 (USB-3000): the raw frame, or the information bits, in a channel packet with the rate for that form.
- A DFSI (TIA-102.BAHA) voice frame record: the IMBE information octets, the error counts and, from the position, which record of the superframe it is.

### Status and discovery

Status goes to port 5006 of the same group, from the same socket as the data, as *radiod* sends it: SSRC, description, the frequency, *radiod*'s signal and noise figures for the voice channel as in the speech stream's status, the clock reference (GPS time and RTP timestamp), sample rate 8000, one channel, the packet counts and, as the encoding, **12**: the first value past those in *rtp.h* (its **UNUSED_ENCODING**), which no ka9q-radio program records or plays. It carries no payload type: *pcmrecord* makes a session from any status and opens a file at the first data packet of the payload type the status names, whatever the encoding, so with no payload type in it the frames match nothing and *pcmrecord* ignores the stream (and *monitor* drops packets of a payload type it knows nothing of). A receiver matches status and data by SSRC and sender, and knows the data by payload type 97 and the version octet. The output level in the status is always minus infinity, so *monitor* never opens its squelch for it.

## Conventional channels

A conventional (non-trunked) P25 channel is just a channel in *radiod*'s configuration that has no control channel: configure it like a control channel (as above), with as many frequencies as you like, in one section or several, on one data group or more. *p25d* decodes every channel on its groups, each in its own thread, so one *p25d* handles any number of them. A conventional channel can also share a group with a trunked control channel: a channel no grant names is decoded as conventional.

Each conventional channel's voice (and frame) stream uses the channel's own SSRC, and its description names the talkgroup (or unit), the source and the NAC, e.g. **P25 TG 2501 src 1118028 NAC 443** (no talker alias here). A telephone interconnect transmission names the radio in the call, with no source: **P25 telephone 1118028 NAC 443**, as on a trunked voice channel. The rule above applies the same way: on late entry, voice waits for the next encryption sync to say it is clear. The talkgroup lists (**-g**, **-x**) choose which trunked calls to follow; they don't filter conventional channels, which you chose by configuring them. **-a** (**--nac**) does: on a frequency shared with another system, give the NAC you want, and the other's transmissions are dropped, as a radio set to that NAC would ignore them.

*p25d* doesn't decode analog FM. On a mixed-mode channel, configure the frequency a second time as an ordinary FM channel (its own section and data group) to hear the analog traffic.

Each transmission on a conventional channel gets a line when it starts, once its talkgroup and source are known (or after four voice units without them: **talkgroup unknown**), and one when it ends, with the same fields as the trunked call lines: talkgroup or unit (**group tg**, **unit tgt**, or **telephone tgt** with the radio in a telephone interconnect call and **src 0**), source, talker alias, emergency and encrypted flags, duration, voice units, words that failed, bits corrected, and how it ended (**terminator**, **timeout**: no voice for half a second past the next voice unit's time, **new transmission**: a header or link control naming another talkgroup or talker, **channel closed**, **p25d shutting down**):
```
Sun 22 Nov 2026 11:23:18.714 UTC ssrc 155250 155.250000 MHz NAC 443 transmission start group tg 2501 src 1118028
Sun 22 Nov 2026 11:23:56.300 UTC ssrc 155250 155.250000 MHz NAC 443 transmission end group tg 2501 src 1118028 after 28.3 s, 156 voice units, 1 words bad, 390 bits corrected, terminator
```
These are new lines; the existing **TDU after ... voice units** and **TDULC after ...** lines are unchanged.

## Output

Decoded events go to standard output, one line each, and everything else (errors, startup messages) to standard error. Every event line starts with the time of the signal (from *radiod*'s clock, to the microsecond, in the same format *packetd* uses; some examples below are shortened to the millisecond), the SSRC and the channel frequency:
```
Sun 22 Nov 2026 08:14:05.443000 UTC ssrc 857981 857.981250 MHz NAC 443 TSBK NET_STS_BCST lra=0x00 wacn=0xbee00 sys=0x445 ch=0-1117 class=0x70
Sun 22 Nov 2026 08:14:05.503000 UTC ssrc 857981 857.981250 MHz NAC 443 TSBK GRP_V_CH_GRANT tg=2501 src=1118028 svc=0x04 prio=4 ch=0-1597 freq=860.987500
Sun 22 Nov 2026 08:14:05.643000 UTC ssrc 857981 857.981250 MHz NAC 443 TSBK IDEN_UP_TDMA iden=2 type=3 tdma=1 slots=2 base=851.012500 spacing=12500 bw=12500 tx_offset=-45000000
```
Trunking messages are always decoded and logged: the message name as in TIA-102.AABC, then its fields. Talkgroups and radio IDs are decimal; NAC, WACN and system ID are hex. A channel prints as *identifier-number*, with its frequency in MHz (and TDMA slot) once the site has broadcast that identifier. An identifier update is taken into the band plan only if its base frequency is between 25 MHz and 1 GHz, its channel spacing is not zero and at most 1 MHz, and its transmit offset is at most 100 MHz either way.

Each call gets one line when it starts and, if followed, one when it ends, on the control channel. They show the kind of call and who is in it (**group tg** *talkgroup*, or **unit tgt**, **telephone tgt** or **data tgt** *radio*, then **src** *source*), the talker alias once known, the voice frequency, the voice channel's SSRC and flags (**emergency**, **encrypted**, **patched**); a call not followed says why; the end gives the duration, voice units, link control and encryption sync words that failed, bits corrected in the voice frames, and why the call ended (**terminator**, **timeout**, **new_call**: the channel granted to another call, **link_control**: the channel's link control naming another call, **control channel lost**, **p25d shutting down**). A call that got no voice says **no voice received** instead of the counts:
```
Sun 22 Nov 2026 09:52:43.509 UTC ssrc 857981 857.981250 MHz NAC 443 call start group tg 2501 src 1118028 voice 860.987500 MHz ssrc 860988
Sun 22 Nov 2026 09:53:15.149 UTC ssrc 857981 857.981250 MHz NAC 443 call end group tg 2501 src 1118028 voice 860.987500 MHz ssrc 860988 after 31.7 s, 156 voice units, 1 words bad, 413 bits corrected, timeout
Sun 22 Nov 2026 14:10:52.503 UTC ssrc 770506 770.506250 MHz NAC 443 call start group tg 2197 src 1113420 voice 769.906250 MHz slot 0 ssrc 769906
Sun 22 Nov 2026 14:11:12.131 UTC ssrc 770506 770.506250 MHz NAC 443 call end group tg 2197 src 1113435 voice 769.906250 MHz slot 0 ssrc 769906 after 4.0 s, 21 voice units, 0 words bad, 35 bits corrected, terminator
Sun 22 Nov 2026 09:52:45.805 UTC ssrc 857981 857.981250 MHz NAC 443 can't follow calls on 857.187500 MHz (ssrc 857188): outside the front end's coverage; not asking for it again
```
A Phase 2 call's voice units are its voice bursts (four or two vocoder frames each), its words bad the 2V bursts whose ESS failed. With **-v** the end of calls not followed is logged too, and site, patch and control channel changes, and what becomes of each voice channel after its last call; with **-vv**, every call update:
```
Sun 22 Nov 2026 09:53:15.149 UTC ssrc 857981 857.981250 MHz NAC 443 voice channel 860.987500 MHz ssrc 860988 kept for 30 s
Sun 22 Nov 2026 09:53:16.402 UTC ssrc 857981 857.981250 MHz NAC 443 voice channel 860.987500 MHz ssrc 860988 reused after 1.3 s
Sun 22 Nov 2026 09:54:16.871 UTC ssrc 857981 857.981250 MHz NAC 443 voice channel 860.987500 MHz ssrc 860988 released: no call for 30 s
Sun 22 Nov 2026 09:55:02.310 UTC ssrc 857981 857.981250 MHz NAC 443 voice channel 860.987500 MHz ssrc 860988 let go, not released: asked for by the site on ssrc 851012
```
The last is a channel kept by one site and asked for by another on the same *radiod* (see **Hang time**).

**Talker aliases.** Two manufacturers' forms are decoded: Motorola's (an alias header and data blocks, in Phase 1 link control or Phase 2 MAC structures, with their CRC checked) and L3Harris's (Phase 1 link control blocks 1 to 4, where blocks 1 and 2 are one copy of the alias and blocks 3 and 4 another; each pair is taken as a whole alias and the latest pair wins; Phase 2 carries the whole alias in one MAC structure). Each new alias is logged on a trunked voice channel, e.g. **NAC 443 talker alias src 1118028 "ENGINE 5"** (Phase 2: **slot 0 talker alias "ENGINE 5"**), and appears in the call lines and the stream description.

A Phase 2 voice channel logs, per timeslot, its MAC PTT and END PTT, each distinct MAC structure (once a couple of seconds), the ESS when its algorithm or key changes, and the end of each transmission:
```
Sun 22 Nov 2026 14:10:54.894 UTC ssrc 769906 769.906250 MHz slot 0 MAC PTT chan=facch tg=2197 src=1113435 algid=0x80 kid=0x0000 mi=000000000000000000
Sun 22 Nov 2026 14:10:56.903 UTC ssrc 769906 769.906250 MHz slot 1 ESS algid=0x84 kid=0x4319 mi=cd23b2486c44d6b700
Sun 22 Nov 2026 14:10:57.035 UTC ssrc 769906 769.906250 MHz slot 0 hangtime after 15 voice bursts (1.1 s), 25 bits corrected
```

A decoded header is logged as it arrives, and so is a terminator after voice (**TDU after 156 voice units (28.1 s), 390 bits corrected**; a terminator with link control gives two lines: the link control, then the terminator). With **-v**, each voice data unit is logged too (**LDU1 ok, 12 voice bits corrected, sync 22.6**; the sync is the frame sync's correlation, 24 at best), as are a terminator with no voice before it and a packet whose header passed its CRC and whose data blocks did not (**PDU data blocks failed CRC, sync 21.3**), and each channel logs a status line every **--update** seconds:
```
Sun 22 Nov 2026 08:15:17.129999 UTC ssrc 857981 857.981250 MHz status: locked, offset +32.9 Hz, filter gentle, syncs 797 weak 2, TSBK 2,335 bad 61, LDU 0, words bad 0, 19,200 Hz, packets 6,000 drops 0 dupes 0 filled 0 resyncs 0 overruns 0
```
A Phase 2 channel's line instead gives (for a control channel, after **Phase 2 control** and the LCCH's timeslot) frame sync, carrier offset, whether the scrambling parameters are set, fragments received and missed, and per timeslot the voice frames and the MAC messages that passed and failed their checks. The Phase 1 line shows whether frame sync is held, the estimated carrier offset from the channel frequency, the receive filter in use, frame syncs found (and those accepted on a weak match because the NAC agreed), trunking blocks that passed and failed their CRC, voice data units, header, link control and encryption sync words that failed to decode, and the stream counters: packets received, lost, duplicated, zero samples filled in for lost packets, gaps too long to fill, and blocks dropped because the decoder fell behind. The thousands separators appear only under a locale that groups digits (**-l**, or $LANG). With **-vv**, trunking blocks and packet headers that failed their CRC, and headers and terminator link control that did not decode, are logged too.

## Running as a service

```
sudo systemctl enable --now p25d@p25-iq.local
tail -f /var/log/p25d.log
```
The instance name is the multicast group. All instances append to **/var/log/p25d.log**; standard error goes to the journal (**journalctl -u p25d@p25-iq.local**). For voice output or other options, override **ExecStart** with **systemctl edit p25d@p25-iq.local**, e.g. **ExecStart=/usr/local/sbin/p25d -R p25-pcm.local -F p25-frames.local %i** (after an empty **ExecStart=** line; the Debian package installs it as **/usr/sbin/p25d**).

## Notes and credits

### Things to know

- **What has been tested.** Phase 1 was tested live on the air on a VHF L3Harris linear simulcast trunked system at a weak signal (one trunking block in ten failing its CRC), with only the control channel configured in *radiod*: *p25d* asked for each granted voice channel, kept it for the hang time, reused it and released it. **Phase 2 has not been tested live on the air.** Phase 2 voice and the Phase 2 control channel have been tested only from a recording of a real Phase 2 voice channel and from generated signals, both through a real *radiod*.
- **The vocoder is optional, and not a complete one.** mbelib is used only if it is found when *p25d* is built (see **The vocoder**). mbelib decodes the vocoder parameters, enhances the spectral amplitudes and synthesises voiced speech with phase regeneration as the standards describe, but it takes shortcuts (checked for IMBE in mbelib 1.3.0): unvoiced bands are made from a few random-phase sinusoids and a little noise instead of shaped white noise, which is the audible difference; the standard's adaptive smoothing of voicing decisions and spectral amplitudes at high error rates is absent; silence frames are not treated as such (*p25d* treats them as repeats); and it uses the C library's **rand()**, so its output is not repeatable bit for bit. Its own frame repeat rule is not used: *p25d* applies the standard's repeat and mute rules itself. The vocoder is called through a small interface (the **p25_vocoder_** functions in *p25audio.c*), so a complete implementation can take its place, and **-F** gives the frames to a vocoder of your own. The author has one that follows the specification more closely, but it is not yet packaged for distribution. mbelib's README says it is for educational purposes only and that the algorithms may be covered by patents, so packagers may prefer to build without it.
- **At a weak signal a damaged word can pass its error correction with wrong contents.** On the air about 0.7% of the encryption syncs that decoded carried values the system never sends; a few of those, and two voice headers, said unencrypted. The Reed-Solomon stage accepts whatever it can complete, erasures included, as the codes allow. The effects are a wrong line in the log, now and then a call record with no voice, and a moment of an encrypted transmission decoded as noise, or of a clear one muted, until the next sync. This is left so on purpose, to keep the rule for encrypted voice simple and the decoder as sensitive as the codes permit.
- **More than one system.** A trunked group call's stream has the talkgroup number as its SSRC, and talkgroup numbers are unique only within one system. Run one *p25d*, with its own output group, per system.
- **Control channel rotation needs every possible control channel configured, for now.** See **Control channel rotation**. A later version is to ask *radiod* for the site's announced secondary control channels when the control channel goes silent, so that only one need be configured.
- **One front end per system, for now.** *radiod* serves one front end per instance, and *p25d* asks for voice channels from the *radiod* that sends the control channel, so the control channel and every voice channel it grants must lie within that one front end's coverage; a call on a frequency outside it is logged and not followed. A system whose channels span more than one tuner's bandwidth needs *p25d* to work with more than one *radiod* at once: for each granted frequency, find the *radiod* whose front end covers it, ask that one for the channel, and decode its stream with the rest. That is planned, not yet done.
- **A composite control channel is not handled.** On some sites, typically small ones with few channels, the control channel can itself be given to a call as its voice channel: while that call lasts the frequency carries the call's voice instead of trunking messages, and it becomes the control channel again afterwards. *p25d* logs such a call but does not decode it (the channel is already its control channel, so the call ends with no voice received); it takes the voice there as the control channel having been lost, and finds it again when trunking messages return.
- **Other known limits.** The deny list (**-x**) tests only a call's own talkgroup, while the allow list (**-g**) tests every member of a patch. Two calls on one frequency from two systems heard at once give the second one no voice.
- **The frame stream's numbers are ours.** RTP payload type 97 and encoding value 12 are not in ka9q-radio's *rtp.h*; no other ka9q-radio program reads the stream, and the numbers may change if the package assigns them.
- **TTL and [global].** *radiod* makes a voice channel asked for on demand from its **[global]** section: **data =** must be set there, and **ttl =** there is the TTL of those channels, which a request cannot change. *p25d*'s own voice and frame output has TTL 0 (this host only) unless **-T** says otherwise.
- **A *radiod* defect this runs into.** A channel created by a command that also changes its sample rate from the template's sends its first packets with the template's payload type. The first data of the channel's own type also leaves *radiod* just before the status that names the type. *p25d* takes or drops each of those first packets according to what it knows of its payload type when it arrives, and asks *radiod* (by sending the encoding again) to correct the type. This is a few tens of milliseconds at the start of a new channel, before any voice; decoding is not affected.
